# Phase 09.1 Plan 09: Claim Generation + CSRF Summary

`POST /api/v1/claim_generation` upgraded from the plan-09.1-03 501 stub to
the full atomic flow per D-04 / RESEARCH §9. A single
`db.transaction(...)` claims `anonymous_generations` rows owned by the
caller's anon cookie, re-tags any anon ephemeral deployments via
`retagScript()`, clears `expires_at` + `anon_session_id`, and (after
commit) issues `Set-Cookie: mcpgen_anon_session=; Max-Age=0`. Hono
`csrf({ origin: fn })` middleware lands on `protectedApp` BEFORE
`authMiddleware`, completing the T-9.1-claim defence-in-depth (fixation
re-issue from plan 09.1-03 + transactional UPDATE WHERE claimed_at IS
NULL + Origin allowlist).

**Atomicity guarantee:** all DB writes + retag calls run inside one
`db.transaction(...)` block. If `retagScript` throws (CF API down /
rate-limited / network error), the transaction aborts and the
`deployments.expires_at` + `deployments.anon_session_id` columns remain
NOT NULL. The cleanup cron (plan 09.1-10) picks up the row on its next
cycle and hard-deletes both the DB row and the CF script —
**eventually consistent**, never half-claimed.

## CSRF Middleware Mount Order + Origin Allowlist

```typescript
// apps/api/src/index.ts (buildApp factory, layer 5)
const protectedApp = new Hono<{ Bindings; Variables }>();

const csrfMiddleware = csrf({
  origin: (origin) => {
    if (origin === 'https://mcpgen.app') return true;
    if (/^https:\/\/mcpgen-.*\.vercel\.app$/.test(origin)) return true;
    if (process.env['NODE_ENV'] !== 'production' && origin === 'http://localhost:3000') return true;
    return false;
  },
});

// Origin-presence guard — production browsers always send Origin on
// non-GET cross-origin POST. Server-side fetch + same-origin XHRs do not.
protectedApp.use('*', async (c, next) => {
  if (c.req.header('origin') === undefined) { await next(); return; }
  await csrfMiddleware(c, next);
});
protectedApp.use('*', authMiddleware);
```

| Origin                              | csrf decision | Rationale                                                       |
| ----------------------------------- | ------------- | --------------------------------------------------------------- |
| `https://mcpgen.app`                | ✓ allow       | Production canonical hostname                                   |
| `https://mcpgen-pr-123.vercel.app`  | ✓ allow       | Vercel preview deploys (PR-scoped subdomains)                   |
| `http://localhost:3000` (non-prod)  | ✓ allow       | Local Next.js dev server                                        |
| `http://localhost:3000` (prod)      | ✗ reject      | Production must not trust localhost                             |
| `https://evil.com`                  | ✗ reject      | Cross-origin attacker — primary T-9.1-claim threat              |
| (no Origin header)                  | ✓ pass-through | Server-side fetch + same-origin XHRs (Origin-presence guard)   |

**Hono csrf trigger condition:** the middleware only inspects requests
with form-style `Content-Type` (`text/plain`, `application/x-www-form-
urlencoded`, `multipart/form-data`). JSON POSTs are not CSRF-vulnerable
because cross-origin JSON requires a CORS preflight that the browser
will block on a missing `Access-Control-Allow-Origin` response. JSON
traffic flows past csrf untouched — by design, NOT a gap.

## T-9.1-08-06 Race Regression Result

The cleanup cron (plan 09.1-10) reads:

```sql
SELECT id, cf_worker_name FROM deployments
WHERE expires_at IS NOT NULL
  AND anon_session_id IS NOT NULL
  AND expires_at < NOW();
```

**Race scenario:** anon ephemeral deployment is past `expires_at` AND
the user simultaneously signs up. Without atomicity, the cleanup cron
could read the row pre-claim while the claim transaction is mid-write,
issuing a `deleteScript` AFTER the claim has retagged the script as
permanent.

**Mitigation:** the claim transaction clears BOTH `expires_at` and
`anon_session_id` in a single atomic `UPDATE`. The cleanup query reads
both fields with `IS NOT NULL`, so it sees the row as either:
- pre-claim (`expires_at NOT NULL AND anon_session_id NOT NULL`) — proceeds with delete
- post-claim (`expires_at NULL AND anon_session_id NULL`) — skips

Never both.

**Tests:**
- `claim-generation.test.ts` test 11 (in-memory mock): cleanup query
  returns 0 rows after claim transaction.
- `claim-flow-e2e.test.ts` e2e 3 (live DB, when DATABASE_URL set):
  backdates `expires_at` past `NOW()`, runs claim, runs cleanup query
  scoped to seeded deployment id — 0 rows.

## Decisions Made

1. **Hono `csrf()` middleware over hand-rolled origin check.** RESEARCH
   §9 ranked three options: bare Origin check, Hono csrf middleware, and
   double-submit signed cookie. Hono csrf is one line, framework-blessed,
   and protects all future protectedApp POST endpoints uniformly.
2. **Origin-presence guard wrapper around csrf.** Without it, every
   protected POST that omits `Content-Type` (defaulting to `text/plain`)
   gets rejected because Hono csrf treats missing Origin + missing
   Sec-Fetch-Site as "not allowed". Production browsers always send
   Origin on non-GET cross-origin POST, so absence = same-origin or
   server-side. The wrapper preserves CSRF protection where it matters
   (browser cross-origin) and keeps server-side traffic flowing.
3. **Single transaction for claim + retag + clear.** retagScript runs
   inside the transaction; CF retag failure aborts DB writes. Eventual
   consistency: cleanup cron picks up the row next cycle. This avoids
   the alternative (separate transactions) which would create a window
   where a CF retag succeeded but the DB wasn't cleared, leaving the
   row matchable by the cleanup query.
4. **Smoke 7 in `anon-endpoint-smoke.test.ts` updated from 501 → 200.**
   The plan-09.1-03 stub assertion was specifically marked "plan 09.1-09
   fills the real flow" — replacing the assertion is the canonical
   plan-09 deliverable, not a test-loosening regression.

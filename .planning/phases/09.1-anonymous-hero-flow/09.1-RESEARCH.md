## Summary

Phase 9.1 reverses the silent Phase-8 regression that gates all `/api/v1/*` behind Logto JWT, restoring the anonymous 60-second hero flow promised in `docs/mcpgen-ux-flow.md` §1.1. The technical fight is **boundary repositioning, not new infrastructure** — every primitive needed (Hono sub-app middleware composition, TimescaleDB hypertable, Inngest crons, CF dispatch namespace tags, Postgres source-of-truth claim) already exists in Phases 1–9 code.

Three concrete risks surfaced in research:

1. **CF Workers for Platforms charges per-script after 1000-script free tier** ($0.02/script/month). Anon ephemeral tenants tagged `expires_at=NOW()+24h` accumulate and bill if cleanup cron fails. Cleanup cron must run reliably and must use the official `DELETE /accounts/.../scripts/{name}` endpoint — there is **no Wrangler CLI flag for tagged deletion**, only the API. ([CITED: Cloudflare Workers for Platforms pricing](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/reference/pricing/))
2. **Neon does NOT support TimescaleDB compression** — `anon_generation_log` after-7d compression policy in CONTEXT D-09 is not implementable on Neon. Use `drop_chunks()` retention instead (matches CONTEXT D-06 30d retention on rate-limit log already). ([CITED: Neon TimescaleDB docs](https://neon.com/docs/extensions/timescaledb))
3. **`@mcpgen/cache/keys.py:_canonicalize` already implements `json.dumps(spec_dict, sort_keys=True, separators=(",", ":"))`** for `spec_hash` — Phase 9.1 cache hit lookup MUST reuse this exact function (already running in Stage A) rather than re-implementing RFC 8785. Confirmed in `apps/generation-engine/src/mcpgen_engine/stages/stage_a.py:500-505`.

**Primary recommendation:** Treat this phase as a thin compositional refactor over existing Phase 1–9 primitives. Five of the 12 founder questions resolve by referencing existing code; only sections 1, 3, and 8 require external library/API verification before planning.

## 1. Anon-session cookie best practices (2026)

### Verified facts

**Hono on CF Workers cookie helpers:** `setCookie(c, name, value, options)` from `hono/cookie` produces standard `Set-Cookie` headers compatible with CF Workers' Response model. Signed variant `setSignedCookie(c, name, value, secret, options)` uses HMAC-SHA-256 via WebCrypto (returns Promise). [CITED: https://hono.dev/docs/helpers/cookie]

**Cookie size limits on CF Workers:** As of 2025-10-16, Cloudflare raised total HTTP header limit to **128 KB** (was 32 KB). No separate cookie-specific limit — cookies count against header total. A 26-char ULID + ~20 chars of overhead fits comfortably. [CITED: https://developers.cloudflare.com/changelog/2025-10-16-header-limit-increase/]

**`__Host-` prefix support in Hono:** `setCookie(c, name, value, { prefix: 'host', secure: true, path: '/', httpOnly: true })`. The prefix forbids `Domain` attribute and forces `Secure` + `Path=/`, which are precisely the constraints for our anon session. [CITED: https://hono.dev/docs/helpers/cookie]

**SameSite=Lax vs Strict for anon→signup claim:**
- `Strict` blocks the cookie on cross-site navigation including the Logto OAuth redirect-back (`logto.example.com` → `mcpgen.app/callback`). The cookie WOULD be missing on the post-signup landing → claim would fail.
- `Lax` sends the cookie on top-level GET navigations (the OAuth redirect IS a top-level GET). This is required for the claim flow to work.
- Conclusion: **`SameSite=Lax` is the only viable choice** (matches CONTEXT D-04 + Phase 7 D-19). Don't even consider Strict.
[CITED: OWASP CSRF prevention cheat sheet]

### Recommended cookie shape

```typescript
// apps/api/src/routes/v1/generate.ts (anon path)
import { setCookie, getCookie } from 'hono/cookie';
import { ulid } from 'ulid';

const ANON_COOKIE_NAME = 'mcpgen_anon_session';
const ANON_COOKIE_MAX_AGE_SEC = 7 * 24 * 60 * 60; // 7 days per D-04

function ensureAnonSession(c: Context): string {
  const existing = getCookie(c, ANON_COOKIE_NAME);
  if (existing && /^[0-9A-HJKMNP-TV-Z]{26}$/.test(existing)) return existing;

  const id = ulid();
  setCookie(c, ANON_COOKIE_NAME, id, {
    httpOnly: true,
    sameSite: 'Lax',
    secure: c.env.ENVIRONMENT === 'production',
    path: '/',
    maxAge: ANON_COOKIE_MAX_AGE_SEC,
    // No `prefix: 'host'` — frontend (Vercel) and BFF (CF Workers)
    // are different hosts in production, so __Host- on a same-domain
    // proxy path works, but on cross-host it forces re-thinking the
    // origin model. Phase 9.1 recommendation: SKIP __Host- in MVP,
    // re-evaluate in Phase 10 once production domain is final.
  });
  return id;
}
```

**Notes:**
- `secure: c.env.ENVIRONMENT === 'production'` matches the conditional pattern in `infrastructure/logto/README.md` env contract.
- `maxAge` (in seconds) is preferred over `expires` for proxy-friendliness.
- ULID format check (Crockford base32, 26 chars) prevents cookie-pollution attacks; reject silently and re-issue.
- Session-fixation mitigation per CONTEXT D-04: re-issue on cold-start landing visit (not just any GET) — implementation detail = check `Referer` header, if absent or off-origin reissue. Plan target.

## 2. Per-route auth in Hono (D-07)

### Verified pattern

**Canonical Hono per-route auth via mounted sub-apps:** [CITED: https://hono.dev/docs/api/routing]

```typescript
// apps/api/src/index.ts (refactor target per D-07)
import { Hono } from 'hono';
import { authMiddleware, type AuthEnv, type AuthContext } from './middleware/auth.js';

interface Bindings extends AuthEnv {
  // ... existing Phase 1–9 bindings
  BFF_ANONYMOUS_GATE: 'playground' | 'preview' | 'quality' | 'deploy';
}
interface Variables { auth?: AuthContext }

const app = new Hono<{ Bindings: Bindings; Variables: Variables }>();

// ─── PUBLIC routes (no auth) ─────────────────────────────────────
// Mount BEFORE protectedApp registration so middleware ordering is correct.
app.route('/api/v1/generate', generateRoute);              // anon-allowed (D-08)
app.route('/api/v1/jobs', jobsAnonRoute);                  // cookie-scoped within
app.route('/api/v1/deploy/ephemeral', ephemeralDeployRoute); // anon-allowed
// Stripe webhook stays unprotected (signature is its own auth)
app.route('/api/v1/stripe/webhook', stripeWebhookRoute);

// ─── PROTECTED routes (Logto JWT required) ───────────────────────
const protectedApp = new Hono<{ Bindings: Bindings; Variables: Variables }>();
protectedApp.use('*', authMiddleware);  // applies to ALL routes mounted on protectedApp
protectedApp.route('/playground', playgroundRoute);
protectedApp.route('/download', downloadRoute);
protectedApp.route('/deploy/permanent', permanentDeployRoute);
protectedApp.route('/dashboard', dashboardRoutes);
protectedApp.route('/billing', billingRoutes);
protectedApp.route('/claim_generation', claimRoute);  // JWT + reads anon cookie

// Mount protectedApp at /api/v1 — its sub-routes inherit the middleware
app.route('/api/v1', protectedApp);

export default app;
```

### Critical ordering gotchas [CITED: Hono routing docs]

1. **`apiRoutes.use('*', authMiddleware)` MUST be called BEFORE `app.route('/api/v1', apiRoutes)`** — otherwise middleware doesn't apply to sub-routes. Verified in Hono docs verbatim quote: "Handlers or middleware will be executed in registration order".
2. **Public routes MUST be mounted on `app` BEFORE `app.route('/api/v1', protectedApp)`** — first match wins. If `/api/v1/generate` is mounted BOTH on `app` (public) AND on `protectedApp` (protected) and `protectedApp` is mounted first, the public registration is shadowed.
3. **Variable typing propagates via Hono generic** — `Hono<{ Variables: { auth?: AuthContext } }>` on the parent allows handlers to read `c.var.auth` without cast. The existing `apps/api/src/middleware/auth.ts` uses `createMiddleware<{ Variables: { auth: AuthContext } }>` — when applied to `protectedApp`, `c.var.auth` is non-nullable inside protectedApp handlers; on public handlers `c.var.auth` is undefined. This typing must propagate via `new Hono<{ Bindings, Variables }>()` declarations.

### `BFF_ANONYMOUS_GATE` env-var implementation

The flex requirement in D-01 ("config switch, not hardcoded") is implementable as a registration-time decision:

```typescript
// apps/api/src/index.ts — gate-position router
function buildApp(env: Bindings): Hono {
  const app = new Hono<{ Bindings: Bindings; Variables: Variables }>();
  const protectedApp = new Hono<{ Bindings: Bindings; Variables: Variables }>();
  protectedApp.use('*', authMiddleware);

  const gate = env.BFF_ANONYMOUS_GATE ?? 'playground';

  // Always public
  app.route('/api/v1/generate', generateRoute);
  app.route('/api/v1/jobs', jobsAnonRoute);
  app.route('/api/v1/deploy/ephemeral', ephemeralDeployRoute);

  // Conditionally public based on gate
  if (gate === 'deploy') {
    app.route('/api/v1/playground', playgroundRoute);
    app.route('/api/v1/preview', previewRoute);
    app.route('/api/v1/quality', qualityRoute);
  } else if (gate === 'quality') {
    app.route('/api/v1/preview', previewRoute);
    app.route('/api/v1/quality', qualityRoute);
    protectedApp.route('/playground', playgroundRoute);
  } else if (gate === 'preview') {
    app.route('/api/v1/preview', previewRoute);
    protectedApp.route('/quality', qualityRoute);
    protectedApp.route('/playground', playgroundRoute);
  } else { // 'playground' (default)
    protectedApp.route('/playground', playgroundRoute);
  }

  // Always protected
  protectedApp.route('/download', downloadRoute);
  protectedApp.route('/deploy/permanent', permanentDeployRoute);
  protectedApp.route('/dashboard', dashboardRoutes);
  protectedApp.route('/billing', billingRoutes);
  protectedApp.route('/claim_generation', claimRoute);

  app.route('/api/v1', protectedApp);
  return app;
}

export default {
  fetch: (req: Request, env: Bindings, ctx: ExecutionContext) =>
    buildApp(env).fetch(req, env, ctx),
};
```

**Test for the env-var flex requirement:** `BFF_ANONYMOUS_GATE=preview pnpm test` should make a vitest case "anon GET /api/v1/preview/:id returns 200" pass; same case under `BFF_ANONYMOUS_GATE=playground` (default) returns 401. This is the founder-stated acceptance criterion.

**Why this works with `apps/api/src/middleware/auth.ts` unchanged:** the existing middleware reads `c.req.header('Authorization')` and rejects 401 on missing/invalid bearer. By NOT mounting authMiddleware on the public routes, anon requests succeed at the route handler level (where the cookie + rate limit logic lives). The middleware itself is unchanged.

## 3. Cloudflare Workers for Platforms anon-tenant lifecycle

### Verified facts

**Single namespace can hold unlimited scripts.** [CITED: https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/reference/limits/] — *"Cloudflare provides an unlimited number of scripts for Workers for Platforms customers."*

**Pricing: $0.02 per script after 1000-script free tier.** [CITED: https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/reference/pricing/]

> 1000 scripts +$0.02 per additional script

**Cleanup mechanism: REST API `DELETE`.** [CITED: https://developers.cloudflare.com/api/resources/workers_for_platforms/subresources/dispatch/subresources/namespaces/]

```bash
curl -X DELETE \
  "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/workers/dispatch/namespaces/$NAMESPACE_NAME/scripts/$SCRIPT_NAME" \
  -H "Authorization: Bearer $API_TOKEN"
```

**Tags via metadata field on PUT.** [CITED: same Cloudflare API docs]

```bash
curl -X PUT \
  "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/workers/dispatch/namespaces/$NAMESPACE_NAME/scripts/$SCRIPT_NAME" \
  -H "Authorization: Bearer $API_TOKEN" \
  -F 'metadata={"main_module":"worker.mjs","tags":["anon=true","expires_at=2026-05-02T00:00:00Z","session=01HX..."]};type=application/json' \
  -F 'worker.mjs=@worker.mjs;type=application/javascript+module'
```

There is also a dedicated **Put Script Tags** endpoint for updating tags on an already-deployed script:

```
PUT /accounts/{account_id}/workers/dispatch/namespaces/{namespace}/scripts/{script}/tags
```

Useful for the **claim re-tagging step** (D-04 step 5b: anon-cloud-tenants get re-tagged to permanent on signup).

### Decision: namespace strategy — VERIFIED resolution of OQ-1

**OQ-1 from CONTEXT:** Does anon tenant in `mcpgen-prod` count against the same dispatch limit, or do we need a 4th `mcpgen-anon` namespace?

**Answer: anon tenants go in the same `mcpgen-prod` namespace, tagged with `anon=true`.** Reasons:

1. **Pitfall #11 (3-namespace cap with `cf-namespace-guard` pre-commit):** the cap is by environment (prod/staging/sandbox), not by purpose. A 4th namespace would break the pre-commit guard AND require a paired decision-doc bump per the existing pattern.
2. **Tags solve the same organizational problem:** `tag:anon=true` filtering for cleanup-cron query is functionally equivalent to a separate namespace, without the structural cost.
3. **Pricing model is per-script, not per-namespace:** there is no per-namespace fee, so splitting doesn't save money.
4. **Dispatch limits are per-script CPU/request, not per-namespace:** [CITED: CF Workers limits] — anon tenants in shared namespace don't reduce capacity for permanent ones beyond their own per-script consumption.

**Verdict:** OQ-1 resolves to "single namespace + tags". No 4th namespace. Plan 09.1-08 implements tagging.

### Cost estimate for anonymous tier

- Free 1000-script allowance covers steady-state (1000 simultaneously-living anon tenants).
- 24h expiry + cleanup cron means at any time, max(N) anon tenants ≤ (anon gens/day × 1) ≤ rate limit × IP count.
- With 1/IP/24h rate limit (D-02), even 5000 unique IPs/day → 5000 anon scripts at peak with 24h hold → 4000 over free tier × $0.02 = **$80/day worst-case** if cleanup fails. Cleanup MUST be reliable.
- Realistic load: <500 anon gens/day for first 6 months → $0/month from this dimension.

**Risk:** if cleanup cron silently fails for a week, billing surprise. Mitigation: BetterStack alert on cleanup-cron failure (Phase 9 pattern). Plan target: 09.1-10 includes alerting.

### Cleanup cron template (Inngest)

```typescript
// apps/api/src/inngest/functions/anon-tenant-cleanup.ts
import { sql } from 'drizzle-orm';
import { INNGEST_FUNCTION_IDS } from '@mcpgen/contracts/inngest-functions';
import { inngest } from '../client.js';
import { db } from '../../db.js';

export const anonTenantCleanup = inngest.createFunction(
  {
    id: INNGEST_FUNCTION_IDS.ANON_TENANT_CLEANUP, // 'anon-tenant-cleanup-v1'
    triggers: [{ cron: '*/15 * * * *' }],         // every 15 min
  },
  async ({ step }) => {
    const expired = await step.run('list-expired', async () => {
      const r = await db.execute(sql`
        SELECT id, cf_worker_name, dispatch_namespace
        FROM deployments
        WHERE expires_at IS NOT NULL
          AND expires_at < NOW()
          AND anon_session_id IS NOT NULL
        LIMIT 500
      `);
      return r.rows as { id: string; cf_worker_name: string; dispatch_namespace: string }[];
    });

    if (expired.length === 0) return { deleted: 0 };

    // Delete from CF + DB. Each iteration is one Inngest step (durable retry).
    let deleted = 0;
    for (const d of expired) {
      await step.run(`delete-cf-${d.id}`, async () => {
        const url = `https://api.cloudflare.com/client/v4/accounts/${ACCOUNT_ID}/workers/dispatch/namespaces/${d.dispatch_namespace}/scripts/${d.cf_worker_name}`;
        const res = await fetch(url, {
          method: 'DELETE',
          headers: { 'Authorization': `Bearer ${CF_API_TOKEN}` },
        });
        if (!res.ok && res.status !== 404) {
          // 404 = already gone, treat as success
          throw new Error(`CF delete failed ${res.status}: ${await res.text()}`);
        }
      });
      await step.run(`delete-db-${d.id}`, async () => {
        await db.execute(sql`DELETE FROM deployments WHERE id = ${d.id}`);
      });
      deleted += 1;
    }
    return { deleted };
  },
);
```

**Notes:**
- Process ≤500 per run to stay within Inngest step time bounds (default 3min).
- Each script delete is its own step → individual failures retry independently.
- 404 response treated as success (idempotent).
- Inngest function ID `anon-tenant-cleanup-v1` MUST be added to `packages/contracts/src/inngest-functions.ts` register per Phase 8 D-27 pattern (CTRL-09 orphan audit).

## 4. TimescaleDB hypertable for IP rate-limit log

### Verified facts

**Neon supports TimescaleDB Apache-2 features only.** [CITED: https://neon.com/docs/extensions/timescaledb]

> Only Apache-2 licensed features are supported. Compression is not supported.

This means:
- ✅ Hypertables (`create_hypertable`) — supported
- ✅ Time-based retention via `drop_chunks()` — supported
- ❌ Native compression policies (`add_compression_policy`) — **NOT supported on Neon**
- ❌ Continuous aggregates with `materialized` mode — partial support

**Implication for CONTEXT D-09 + D-06:** the CONTEXT-mentioned "Compression policy after 7d" in the objective is **not implementable on Neon**. Plan target must use `drop_chunks()` retention instead. Since CONTEXT D-06 already specifies 30-day retention on `anon_generation_log`, the right approach is **retention-only, no compression**. This matches the existing `usage_events` hypertable pattern in `infrastructure/neon/migrations/20260427000000_init_schema.sql` (already deployed).

### Recommended migration shape

```sql
-- infrastructure/neon/migrations/<timestamp>_phase09_1_anon_flow.sql
-- (Use a timestamp AFTER the latest Phase-8/9 migration per Pitfall #18.)

-- 1. Anonymous session tracking
CREATE TABLE anonymous_generations (
  anon_session_id   TEXT PRIMARY KEY,         -- ULID
  generation_id     UUID NOT NULL REFERENCES generations(id) ON DELETE CASCADE,
  ip_hash           TEXT NOT NULL,             -- sha256(daily_salt + raw_ip)
  created_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  claimed_at        TIMESTAMPTZ,
  claimed_by_org_id UUID REFERENCES organizations(id) ON DELETE SET NULL
);
CREATE INDEX anon_gen_session_idx ON anonymous_generations(anon_session_id);
CREATE INDEX anon_gen_unclaimed_idx ON anonymous_generations(created_at)
  WHERE claimed_at IS NULL;  -- partial index for cleanup cron

-- 2. Rate-limit log — TimescaleDB hypertable
CREATE TABLE anon_generation_log (
  id           BIGSERIAL,
  ip_hash      TEXT NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
SELECT create_hypertable(
  'anon_generation_log',
  'created_at',
  chunk_time_interval => INTERVAL '1 day'  -- daily chunks for tight drop_chunks
);
-- Index strategy per founder objective: (ip_hash, created_at DESC) for the
-- "count rows where ip_hash=$1 AND created_at >= NOW() - INTERVAL '24h'" query.
CREATE INDEX anon_log_ip_time_idx ON anon_generation_log(ip_hash, created_at DESC);

-- 3. Daily-rotating salt storage
CREATE TABLE app_secrets (
  key          TEXT PRIMARY KEY,
  value        TEXT NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  rotates_at   TIMESTAMPTZ
);
-- Salts: app_secrets WHERE key LIKE 'daily_salt_%'.
-- Two rows during grace window (current + previous) per D-11.

-- 4. Extend deployments for ephemeral anon tenants
ALTER TABLE deployments
  ADD COLUMN anon_session_id TEXT REFERENCES anonymous_generations(anon_session_id) ON DELETE SET NULL,
  ADD COLUMN expires_at      TIMESTAMPTZ;
CREATE INDEX deploy_expires_idx ON deployments(expires_at) WHERE expires_at IS NOT NULL;
```

**Notes:**

1. `BIGSERIAL` not `id UUID PRIMARY KEY` for `anon_generation_log` — high insert rate, no need for global uniqueness.
2. `chunk_time_interval => INTERVAL '1 day'` is critical: with the founder's 30-day retention, this gives 30 chunks. `drop_chunks` can drop a whole chunk atomically. Default 7-day chunks would mean only 4 chunks at any time — coarser retention granularity (drop 25% of data per call vs ~3.3%).
3. **Hypertable + UNIQUE constraint quirk:** TimescaleDB requires every UNIQUE index to include the partitioning column (`created_at`). This is why `usage_events` schema in `db-schema.ts` already encodes `(deployment_id, idempotency_key, time)` as the unique. For `anon_generation_log` we don't need a UNIQUE — just an index — so this is moot.
4. Partial index `anon_gen_unclaimed_idx` makes the cleanup cron `WHERE claimed_at IS NULL AND created_at < NOW() - INTERVAL '7 days'` an index scan rather than a sequential scan.

### Recommended salt-rotation cron with grace window

```typescript
// apps/api/src/inngest/functions/anon-salt-rotate.ts
import { sql } from 'drizzle-orm';
import { INNGEST_FUNCTION_IDS } from '@mcpgen/contracts/inngest-functions';
import { inngest } from '../client.js';
import { db } from '../../db.js';

export const anonSaltRotate = inngest.createFunction(
  {
    id: INNGEST_FUNCTION_IDS.ANON_SALT_ROTATE, // 'anon-salt-rotate-v1'
    triggers: [{ cron: '0 0 * * *' }],         // 00:00 UTC daily
  },
  async ({ step }) => {
    // Generate fresh 32-byte random salt (hex-encoded)
    const newSalt = await step.run('generate-salt', async () => {
      const bytes = new Uint8Array(32);
      crypto.getRandomValues(bytes);
      return Array.from(bytes, (b) => b.toString(16).padStart(2, '0')).join('');
    });

    // Atomic two-key write: previous holds old current; current holds new.
    // This implements the "30s grace window" idiomatically — actually a
    // full-day grace because BOTH keys are valid until the NEXT rotation
    // overwrites previous. Per D-11 the founder mentioned 30s, but a full-day
    // grace is no less safe (the previous-day salt is still pseudonymized
    // data), and it removes the race-condition window entirely.
    await step.run('rotate-salts', async () => {
      await db.execute(sql`
        INSERT INTO app_secrets (key, value, rotates_at)
        VALUES ('daily_salt_previous', (SELECT value FROM app_secrets WHERE key = 'daily_salt_current'), NOW() + INTERVAL '24 hours')
        ON CONFLICT (key) DO UPDATE SET value = EXCLUDED.value, rotates_at = EXCLUDED.rotates_at
      `);
      await db.execute(sql`
        INSERT INTO app_secrets (key, value, rotates_at)
        VALUES ('daily_salt_current', ${newSalt}, NOW() + INTERVAL '24 hours')
        ON CONFLICT (key) DO UPDATE SET value = EXCLUDED.value, rotates_at = EXCLUDED.rotates_at
      `);
    });

    return { rotated: true, salt_prefix: newSalt.slice(0, 8) };
  },
);
```

### Hash-with-grace utility (used in BFF rate-limit check)

```typescript
// apps/api/src/lib/anon-ip-hash.ts
import { sql } from 'drizzle-orm';
import { db } from '../db.js';

interface SaltPair {
  current: string;
  previous: string | null;
}

let cachedSalts: { pair: SaltPair; expires_at: number } | null = null;
const SALT_CACHE_TTL_MS = 60_000; // 60s in-memory cache to avoid hot-path SELECT

export async function getCurrentSalts(): Promise<SaltPair> {
  if (cachedSalts && cachedSalts.expires_at > Date.now()) return cachedSalts.pair;
  const r = await db.execute(sql`
    SELECT key, value FROM app_secrets WHERE key IN ('daily_salt_current','daily_salt_previous')
  `);
  const rows = r.rows as { key: string; value: string }[];
  const pair: SaltPair = {
    current: rows.find((x) => x.key === 'daily_salt_current')?.value ?? '',
    previous: rows.find((x) => x.key === 'daily_salt_previous')?.value ?? null,
  };
  cachedSalts = { pair, expires_at: Date.now() + SALT_CACHE_TTL_MS };
  return pair;
}

export async function hashIpForRateLimit(rawIp: string): Promise<string> {
  // Used on INSERT — always uses current salt only.
  const { current } = await getCurrentSalts();
  const buf = new TextEncoder().encode(`${current}:${rawIp}`);
  const digest = await crypto.subtle.digest('SHA-256', buf);
  return Array.from(new Uint8Array(digest), (b) => b.toString(16).padStart(2, '0')).join('');
}

export async function hashIpsForLookup(rawIp: string): Promise<string[]> {
  // Used on SELECT — returns BOTH current and previous hashes so a request
  // arriving moments after rotation still finds yesterday's rate-limit row.
  const { current, previous } = await getCurrentSalts();
  const hashes: string[] = [];
  for (const salt of [current, previous]) {
    if (!salt) continue;
    const buf = new TextEncoder().encode(`${salt}:${rawIp}`);
    const digest = await crypto.subtle.digest('SHA-256', buf);
    hashes.push(Array.from(new Uint8Array(digest), (b) => b.toString(16).padStart(2, '0')).join(''));
  }
  return hashes;
}
```

### Recommended cache-replay timeline

```typescript
// apps/api/src/lib/cache-replay-timeline.ts
import type { GenerationStage } from '@mcpgen/contracts';
import type { QualityReport } from '@mcpgen/ir';
import { ulid } from 'ulid';

export interface CacheReplayEvent {
  readonly job_id: string;
  readonly event_id: string;
  readonly stage: GenerationStage;
  readonly status: 'started' | 'completed';
  readonly partial_result?: Record<string, unknown>;
  readonly delayMs: number;
}

const STAGES: ReadonlyArray<GenerationStage> = [
  'A', 'B', 'C', 'D', 'E', 'F1', 'F2', 'F3', 'completed',
];

// Founder D-05: cache hit replays in <1s. Use small per-stage delay
// (40-120ms) so the user sees progress animation but it's near-instant.
const CACHE_REPLAY_DELAY_MIN_MS = 40;
const CACHE_REPLAY_DELAY_MAX_MS = 120;

interface CachedGen {
  generation_id: string;
  quality_score: number;
  created_at: Date;
  final_tools: unknown;
  quality_report: QualityReport;
}

export function buildCacheReplayTimeline(
  jobId: string,
  cached: CachedGen,
): ReadonlyArray<CacheReplayEvent> {
  const range = CACHE_REPLAY_DELAY_MAX_MS - CACHE_REPLAY_DELAY_MIN_MS;

  return STAGES.map((stage, idx) => {
    const isFirst = idx === 0;
    const isTerminal = stage === 'completed';

    // event_id=0 carries cache_hit metadata per D-05 step 6
    const partial: Record<string, unknown> = isFirst
      ? {
          cache_hit: true,
          original_quality: cached.quality_score,
          original_generation_id: cached.generation_id,
          served_from: cached.created_at.toISOString(),
        }
      : {};

    if (isTerminal) {
      partial.final_tools = cached.final_tools;
      partial.quality_report = cached.quality_report;
    }

    return {
      job_id: jobId,
      event_id: ulid(),
      stage,
      status: isTerminal ? 'completed' : 'started',
      partial_result: Object.keys(partial).length > 0 ? partial : undefined,
      delayMs: CACHE_REPLAY_DELAY_MIN_MS + Math.random() * range,
    };
  });
}
```

### OQ-2 resolution: cache attribution

**OQ-2 from CONTEXT:** When User B is served from User A's cache, is B's `generations` row a fresh row or pointer?

**Answer: fresh row with `cached_from_generation_id` reference.** Reasons:

1. Each anon user has their own `anonymous_generations.generation_id` foreign key — must point at *their own* generation row for proper claim semantics.
2. Quality analytics need to count "served from cache" separately from "ran fresh" — easy with a column.
3. Drift detection: the cached source spec might have changed; `cached_from` lets the drift watcher invalidate downstream rows.
4. Cost tracking: B's row records `llm_cost_usd = 0` (cache hit) which is informationally valuable.

**Schema addition:**

```sql
-- In phase 09.1 migration:
ALTER TABLE generations
  ADD COLUMN cached_from_generation_id UUID REFERENCES generations(id) ON DELETE SET NULL;
CREATE INDEX gen_cached_from_idx ON generations(cached_from_generation_id) WHERE cached_from_generation_id IS NOT NULL;
```

The cache-hit lookup becomes:

```sql
-- BFF anon /generate flow on incoming request
SELECT g.id, g.quality_score, g.quality_report, s.content_hash
FROM generations g JOIN specs s ON s.id = g.spec_id
WHERE s.content_hash = $1                         -- spec_hash (Stage A canonical)
  AND g.quality_score >= 4.0                      -- verified+
  AND g.is_publishable = true
  AND g.created_at >= NOW() - INTERVAL '7 days'  -- freshness
  AND g.cached_from_generation_id IS NULL         -- only ORIGINAL gens, not cache pointers
ORDER BY g.quality_score DESC, g.created_at DESC
LIMIT 1;
```

Then on hit, INSERT a fresh `generations` row with `cached_from_generation_id = <found_id>`, point `anonymous_generations.generation_id` at the new row.

```typescript
  // 1. Auth middleware already validated JWT and set c.var.auth
  const { organizationId } = c.var.auth;
  if (!organizationId) return c.json({ error: 'no_org' }, 403);

  // 2. Read anon cookie
  const anonSessionId = getCookie(c, 'mcpgen_anon_session');
  if (!anonSessionId) return c.json({ error: 'no_anon_session' }, 400);

  // 3. CSRF protection — see "CSRF strategy" below
  const origin = c.req.header('Origin');
  const expectedOrigin = c.env.ENVIRONMENT === 'production'
    ? 'https://mcpgen.app'
    : 'http://localhost:3000';
  if (origin !== expectedOrigin) {
    return c.json({ error: 'origin_mismatch' }, 403);
  }

  // 4. Atomic claim
  const updated = await db.execute(sql`
    UPDATE anonymous_generations
    SET claimed_at = NOW(), claimed_by_org_id = ${organizationId}
    WHERE anon_session_id = ${anonSessionId}
      AND claimed_at IS NULL
    RETURNING generation_id
  `);
  const claimedGenIds = (updated.rows as { generation_id: string }[]).map((r) => r.generation_id);

  // 5. Re-tag any anon-cloud-tenants tied to those generations
  const deployments = await db.execute(sql`
    SELECT id, cf_worker_name FROM deployments
    WHERE generation_id = ANY(${claimedGenIds})
      AND anon_session_id = ${anonSessionId}
      AND expires_at IS NOT NULL
  `);
  for (const d of deployments.rows as { id: string; cf_worker_name: string }[]) {
    await retagScript(c.env, d.cf_worker_name, [
      'anon=false',
      `claimed_by_org=${organizationId}`,
    ]);
  }
  await db.execute(sql`
    UPDATE deployments SET expires_at = NULL, anon_session_id = NULL
    WHERE anon_session_id = ${anonSessionId}
  `);

  // 6. Clear anon cookie
  setCookie(c, 'mcpgen_anon_session', '', {
    httpOnly: true, sameSite: 'Lax', secure: c.env.ENVIRONMENT === 'production',
    path: '/', maxAge: 0,
  });

  return c.json({ claimed: claimedGenIds.length, deployments_retagged: deployments.rows.length });
});
```

### CSRF strategy on `claim_generation`

[CITED: OWASP CSRF prevention cheat sheet]

**Attack vector:** attacker on `evil.com` POSTs to `https://api.mcpgen.app/api/v1/claim_generation` with the victim's cookies (browser auto-attaches cookies on cross-origin POST when `SameSite=Lax`). If the JWT is in a Logto cookie too (also `SameSite=Lax`), both auto-attach → claim succeeds for attacker's own anon session, hijacking the victim's signup.

Wait — actually `SameSite=Lax` does NOT send cookies on cross-origin **POST** (only on top-level GET navigations). So a POST from `evil.com` does not include the Logto cookie. CSRF risk is therefore **low** for `Lax` cookies on POST endpoints.

But OWASP recommends defense-in-depth. **Three options ranked:**

1. **Origin header check (RECOMMENDED, simplest):**
   ```typescript
   const origin = c.req.header('Origin');
   if (origin !== expectedOrigin) return c.json({ error: 'origin_mismatch' }, 403);
   ```
   - Pros: zero infrastructure, zero client-side change, catches the common case.
   - Cons: old browsers without Origin header bypass. Edge case in 2026: <0.1% of traffic.
   [CITED: https://hono.dev/docs/middleware/builtin/csrf — Hono's built-in CSRF middleware works exactly this way]

2. **Hono `csrf()` middleware (also acceptable):**
   ```typescript
   import { csrf } from 'hono/csrf';
   protectedApp.use('*', csrf({ origin: 'https://mcpgen.app' }));
   ```
   Same mechanism, framework-blessed. Recommended over hand-rolled origin check IF we use it on multiple endpoints (e.g., billing/checkout).

3. **Double-submit signed cookie (NOT recommended for MVP):**
   - Adds two server-side state items + one client-side fetch round-trip
   - Required when Origin/Sec-Fetch-Site are unreliable (legacy browsers, certain reverse proxies)
   - Not justified for our single-endpoint risk profile
   - OWASP only mandates this for stateless apps that can't trust Origin

**Phase 9.1 recommendation:** **use Hono's `csrf()` middleware** — applied to `protectedApp` ONCE, protects ALL post-auth endpoints uniformly. Founder's mention of "double-submit cookie pattern OR origin check OR Logto's own CSRF token" — Hono's middleware is the origin-check option, idiomatic and one line.

```typescript
// apps/api/src/index.ts (in buildApp)
import { csrf } from 'hono/csrf';

const protectedApp = new Hono<{ Bindings: Env; Variables: Vars }>();
protectedApp.use('*', csrf({
  origin: c.env.ENVIRONMENT === 'production'
    ? 'https://mcpgen.app'
    : 'http://localhost:3000',
}));
protectedApp.use('*', authMiddleware);
// ... mount routes
```

**Note:** `csrf({ origin })` accepts a string OR a function `(origin, c) => boolean`. For Vercel preview URLs (random subdomains), use the function form:

```typescript
protectedApp.use('*', csrf({
  origin: (origin) => {
    if (origin === 'https://mcpgen.app') return true;
    if (/^https:\/\/mcpgen-.*\.vercel\.app$/.test(origin)) return true;
    if (process.env.NODE_ENV !== 'production' && origin === 'http://localhost:3000') return true;
    return false;
  },
}));
```

## 10. Spec-hash normalization

### Verified facts

**Existing canonicalization in Stage A** (`apps/generation-engine/src/mcpgen_engine/stages/stage_a.py:500-505`):

```python
def _canonicalize(spec_dict: dict[str, Any]) -> str:
    """Deterministic canonicalization for ``spec_hash`` + L1 cache key (Plan 08).

    Sort keys recursively; use the most compact JSON representation.
    """
    return json.dumps(spec_dict, sort_keys=True, separators=(",", ":"))
```

This is `json.dumps(..., sort_keys=True, separators=(",", ":"))` — **the same canonicalization used by `cache/keys.py:_canonical_json_sha256`**. The output is a strict subset of RFC 8785 JCS ([CITED: RFC 8785]) — sufficient for spec_hash equality but lacks RFC 8785's normalized number representation rules.

**For our use case (spec equality comparison, not cryptographic signing) Python's `json.dumps(sort_keys=True, separators=(",",":"))` is equivalent to RFC 8785 JCS.** The differences (number formatting via ECMAScript rules) only matter when comparing across language runtimes. We hash the spec in Python (engine) and **never re-hash in TypeScript (BFF)** — the BFF reads the precomputed `specs.content_hash` from Postgres.

### Recommended approach: REUSE existing function

**Don't add a new dependency.** Don't pull `rfc8785` (Python) or `canonicalize` (npm). The existing `_canonicalize()` in `stage_a.py` is already the canonical hash function for the entire generation pipeline.

**Plan target 09.1-06 should:**

1. Look up cache hit by `specs.content_hash`. The hash is precomputed by Stage A on every `POST /generate`. The BFF cache-hit-check runs Stage A FIRST (cheap, deterministic, $0) for the incoming spec, takes the resulting `spec_hash`, then queries:

   ```sql
   SELECT g.* FROM generations g JOIN specs s ON s.id = g.spec_id
   WHERE s.content_hash = $1
     AND g.quality_score >= 4.0
     AND g.is_publishable = true
     AND g.created_at >= NOW() - INTERVAL '7 days'
     AND g.cached_from_generation_id IS NULL
   ORDER BY g.quality_score DESC
   LIMIT 1;
   ```

2. The Stage A invocation for spec_hash is the SAME call already made before Pass 0 — so cache-check costs $0 incremental work (already part of the pipeline). Stage A early-exit guarantees we don't waste any LLM tokens on a cache hit.

### YAML vs JSON normalization (founder asked)

Stage A explicitly handles both YAML and JSON inputs:

```python
# apps/generation-engine/src/mcpgen_engine/stages/stage_a.py:87-95
spec_text = (await _fetch_spec_text(spec_url) ...)
_parse_spec_text(spec_text)        # accepts YAML or JSON
resolved = _resolve_refs(spec_text) # → Python dict via prance
spec_hash = sha256(_canonicalize(resolved).encode("utf-8")).hexdigest()
```

The hash is computed AFTER YAML/JSON is parsed into a Python dict, then `json.dumps(sort_keys, compact)`. So **YAML and JSON inputs that parse to the same dict yield the same hash automatically.** Whitespace, key ordering, trailing newline differences, YAML anchors expanded — all collapse correctly.

**Verified:** The 2026-04-29 evidence in `apps/generation-engine/src/mcpgen_engine/stages/stage_a.py` confirms this is already production behavior. **Plan 09.1-06 reuses Stage A unchanged.**

## 11. GDPR posture for IP hash

### Verified GDPR analysis

**Article 4(5) definition of pseudonymization** [CITED: GDPR text, https://gdpr-info.eu]:

> processing of personal data in such a manner that the personal data can no longer be attributed to a specific data subject without the use of additional information, provided that such additional information is kept separately and is subject to technical and organisational measures to ensure that the personal data are not attributed to an identified or identifiable natural person.

**Recital 26** [CITED: https://gdpr-info.eu/recitals/no-26/]: pseudonymized data IS still personal data (subject to GDPR), in contrast to truly anonymized data which is not.

**Article 29 Working Party guidance** [CITED: https://www.lexology.com/library/detail.aspx?g=ab4dffdf-f1cc-4f2c-a91c-ce17ac7b6d10]:

> salted and hashed data "reduce[s] the likelihood of deriving the input value," but because "calculating the original attribute value hidden behind the result of a salted hash function may still be feasible within reasonable means," the salted-hashed output should be considered pseudonymized data that remains subject to the GDPR.

### Verdict for `sha256(daily_salt + raw_ip)` with 30d salt rotation

**This qualifies as pseudonymization (NOT anonymization).** Specifically:

1. **WITHIN the 30-day window with current salt available:** the hash is reversible by anyone with the salt and a small IP-space brute-force (IPv4 has 4 billion addresses; sha256 of each is ~1 hour on a single GPU). Anyone with our salt can de-pseudonymize.
2. **AFTER 30 days:** the salt is gone (we delete `daily_salt_previous` after the next-next rotation). Without the salt, a 4-billion-IP-space brute force still works; the hash is "computationally unrecoverable" only against an adversary who lacks BOTH the salt AND an idea of which IPs to try. For practical purposes (our own forensics; an attacker who steals our DB without the salt) — it's effectively anonymized after rotation.

**GDPR-compliant data handling per this design:**
- Pseudonymized PII (Article 4(5)): subject to GDPR for 30 days
- Article 17 erasure: user request → delete all `anon_generation_log` rows where `ip_hash = sha256(current_salt + their_ip)` (we know their IP from session)
- Article 33 breach disclosure: ip_hash leak ≠ raw IP leak; lower severity
- Article 5(1)(c) data minimization: ✓ — we never store raw IP, only the hash with rotating salt

### Privacy policy disclosure (template language)

For Phase 10 plan 10-09 (legal pages):

> **Anonymous abuse prevention.** When you use MCPGen without an account, we hash your IP address with a daily-rotating cryptographic salt and store the hash for 30 days. We never store your raw IP address. The hash lets us prevent abuse of our free tier (one anonymous generation per IP per 24 hours) without identifying you. After 30 days, the salt that produced your hash is deleted, making the data computationally unrecoverable. You can request earlier deletion by emailing privacy@mcpgen.app — provide the IP from which you accessed the service and we will delete matching hashes from the most recent retention window.

**Justifications cited in policy:**
- Lawful basis: Article 6(1)(f) — legitimate interest (preventing service abuse)
- Pseudonymization: Article 4(5)
- Retention period: minimal-necessary-for-purpose (30 days for abuse forensics)
- Data subject rights: Article 17 erasure honored

## Architecture Patterns

### Pattern: Anon-cookie + claim flow

```
Anonymous request flow:
  1. GET / (landing) — no cookie yet
  2. POST /api/v1/generate (paste URL) — BFF generates ULID, sets cookie,
     stores anonymous_generations row, kicks engine job
  3. GET /api/v1/jobs/:id/stream — cookie scopes access; only same anon session
     can read this job's events (or JWT if user signed up mid-stream)
  4. ...all anon screens read via cookie...
  5. POST /api/v1/claim_generation — JWT (Logto) + cookie; atomic UPDATE +
     CFWP retag + cookie clear

Locked invariants:
  - Cookie HttpOnly + SameSite=Lax + Secure (prod) + Path=/ + 7d Max-Age
  - claim_generation route: csrf({ origin: 'mcpgen.app' }) + authMiddleware
  - claim atomicity: single UPDATE...RETURNING in a transaction
  - cookie cleared (Max-Age=0) on success
```

### Pattern: Cache-hit replay timeline

```
Cache lookup (in BFF before Stage A → Pass 0):
  1. spec_hash = await stageA.run(spec_url)  # always run; deterministic + cheap
  2. SELECT FROM generations WHERE content_hash = spec_hash AND quality >= 4.0 ...
  3. If hit:
     a. INSERT new generations row with cached_from_generation_id = found_id
     b. Mark options.cache_hit = true
     c. Return 202 with job_id of the new (cached) row
     d. SSE handler (jobsAnonStreamRoute) detects cache_hit, replays synthetic timeline
        in <1s via buildCacheReplayTimeline()
  4. Else: standard Pass 0..5 + Stage E + F1+F2+F3 pipeline
```

### Anti-Patterns to Avoid

- **Don't:** add a 4th namespace `mcpgen-anon` (violates Pitfall #11). Use tags.
- **Don't:** reimplement RFC 8785 / canonicalize from scratch. Stage A already does it.
- **Don't:** check cookies INSIDE authMiddleware. Keep concerns separate — middleware reads JWT, route handlers read cookies.
- **Don't:** mutate `apps/web/src/{tokens,ui,screen-*}.jsx` content beyond the SSR window guards. ALL anon-state UI text goes via the jsx-bridge wrapper layer (Phase 7 D-10 invariant).
- **Don't:** delete CFWP scripts via `wrangler delete` in Inngest functions — workers can't shell out. Use REST API + `fetch()`.
- **Don't:** truncate `anon_generation_log` for cleanup. Use `drop_chunks()` on the hypertable.

## Common Pitfalls

### Pitfall 1: SameSite=Strict cookie breaks Logto OAuth redirect-back

**What goes wrong:** anon cookie missing on `/callback` after Logto OAuth → claim fails silently → user sees "no generations to claim" message
**Why it happens:** `Strict` blocks cookies on cross-site GETs including OAuth redirects
**How to avoid:** use `SameSite=Lax` (CONTEXT D-04 already locks this; just don't drift)
**Warning signs:** integration test with localhost:3000 ↔ logto endpoint fails on cookie absence

### Pitfall 2: CSRF middleware mounted before authMiddleware blocks legitimate post-auth requests

**What goes wrong:** Hono `csrf()` rejects requests with non-matching Origin BEFORE auth runs. If frontend has a typo in expected origin, all auth requests 403.
**Why it happens:** order matters in middleware composition
**How to avoid:** mount CSRF first (cheap reject) then auth — but `csrf({ origin: fn })` MUST handle all valid origins (production, staging, Vercel preview, localhost dev). Test with `BFF_ANONYMOUS_GATE=preview pnpm test`.
**Warning signs:** all integration tests pass locally, all break on first Vercel preview deploy

### Pitfall 3: Cleanup cron silently fails → CF script count climbs → billing surprise

**What goes wrong:** Inngest function exception → next 24h adds 100s of orphan scripts → 10K-script bill at $0.02/script = $200/month surprise
**Why it happens:** silent failures + lack of "anon scripts in CFWP" dashboard metric
**How to avoid:** BetterStack alert on `anon-tenant-cleanup-v1` failure; weekly script-count audit (count scripts in `mcpgen-prod` matching tag `anon=true`)
**Warning signs:** CFWP billing line item rises week-over-week without anon-traffic increase

### Pitfall 4: TimescaleDB hypertable created with wrong chunk_time_interval

**What goes wrong:** default 7-day chunks → only 4 chunks at any time given 30-day retention → drop_chunks call drops 25% of data → coarse retention
**Why it happens:** `create_hypertable` default is 7 days
**How to avoid:** explicit `chunk_time_interval => INTERVAL '1 day'` (see migration template §4)
**Warning signs:** `SELECT * FROM timescaledb_information.chunks WHERE hypertable_name = 'anon_generation_log'` shows 4 chunks not 30

### Pitfall 5: Salt rotation race — request inflight during 00:00 UTC rotation

**What goes wrong:** request started at 23:59:59 with salt_v1, completes INSERT at 00:00:01 against salt_v2 expectation → rate-limit query at 00:00:02 doesn't find their previous row
**Why it happens:** atomic salt swap is a moment in time
**How to avoid:** the 24h-grace pattern in §5 (BOTH current and previous salts valid for full day after rotation)
**Warning signs:** anon rate-limit telemetry shows brief "spike" of allowed requests at exactly 00:00 UTC daily

### Pitfall 6: `cached_from_generation_id` lookup includes cache-pointer rows → infinite-recursion analytics

**What goes wrong:** "show all generations served from cache" query JOINs cached_from rows back to themselves
**Why it happens:** if cache-hit lookup forgets `AND cached_from_generation_id IS NULL`, a future cache-hit on a cache-pointer row creates a chain
**How to avoid:** the lookup query in §6 includes `AND cached_from_generation_id IS NULL` mandatorily; cache-pointer rows can never themselves be a cache source
**Warning signs:** drift watcher reports "cyclic generation references"; `cached_from_generation_id` chains length > 1

| Session fixation (T-9.1-claim) | Spoofing | Re-issue cookie on cold-start landing visit (no Referer or off-origin) |
| CSRF on `/claim_generation` | Tampering | `hono/csrf` middleware with origin function form |
| IP de-pseudonymization within retention | Information Disclosure | Daily salt rotation; 30d retention limits exposure window |
| Cookie hijack via XSS | Information Disclosure | HttpOnly flag (cookie unreadable from JS) + Sentry CSP |
| Bypass anon rate limit via IPv6 churn | Denial of Service | Out of scope per D-12 (Cloudflare Turnstile deferred); revisit if abused |
| Cache poisoning (User A's bad gen serving as User B's cache hit) | Tampering | `quality_score >= 4.0` floor; `is_publishable = true` filter |
| Anon-tenant cost runaway | DoS (financial) | 24h hard expiry + cleanup cron + BetterStack alert |
| Replay attack on cookie | Spoofing | ULID is one-time-use anon ID; Postgres claim is idempotent (UPDATE ... WHERE claimed_at IS NULL) |

## Why these endpoints

Slack is the canonical "action-rich + workflow-heavy" API used in CONTEXT specifics §D-07.
The fixture covers Channels + Messages + Users because they exercise:

- Smart-ID format coverage (`Message:C0123:ts`, `Channel:C0123`, `User:U0456`)
- Cursor-based pagination (`response_metadata.next_cursor` across `conversations.list`,
  `conversations.history`, `users.list`, `search.messages`)
- 3 action tools: `messages_send` (frequent), `messages_edit` (idempotent), `channels_archive`
  (destructive+idempotent — Slack's canonical "remove" since channels cannot be hard-deleted)
- 1 workflow tool: `send_with_thread_followup` (post message, then threaded reply — exercises
  the workflow-tool conservative-aggregation rule per Pass 4)

## Action verb annotations (Pass 4 verb pattern matching)

- `messages_send`: !destructive, !idempotent (per `_send` Appendix B medium-confidence pattern;
  fixture annotates !idempotent because resending creates a duplicate message)
- `messages_edit`: !destructive, idempotent=true (re-applying same edit is no-op per Slack)
- `channels_archive`: destructive=true, idempotent=true (per `_archive` Appendix B pattern)
- `send_with_thread_followup` (workflow): conservative aggregation across 2 sub-operations —
  !destructive (both sub-ops !destructive), !idempotent (sub-op 1 !idempotent dominates),
  partial_failure_strategy='report' (cannot atomically rollback a posted parent message)

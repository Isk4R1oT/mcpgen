## Why these endpoints

GitHub is the canonical "data-heavy + workflow-rich" API used in CONTEXT specifics
§D-07. The fixture covers Issues + Pull Requests + Releases because they exercise:

- Smart-ID format coverage (`Issue:#42`, `PullRequest:#123`, `Release:rel_...`)
- Pagination via cursor-style `since`/`page` headers (modeled as cursor in fixture)
- 3 action tools (`issues_close`, `pull_requests_merge`, `releases_create`)
- 1 workflow tool (`create_pr_from_branch`) — multi-step coherent task per Pass 1 design

## Action verb annotations (Pass 4 verb pattern matching)

- `issues_close`: destructive=false, idempotent=true (closing a closed issue is no-op)
- `pull_requests_merge`: destructive=false, idempotent=false (merging twice is rejected)
- `releases_create`: destructive=false, idempotent=false (re-create rejected on tag conflict)
- `create_pr_from_branch` (workflow): destructive=false (worst-case across 2 sub-ops)

## Endpoints intentionally excluded

- `/repos/{owner}/{repo}/actions/*` — Actions API has its own surface (~80 endpoints)
- `/orgs/{org}/*` — org admin orthogonal to issue/PR data flow
- `/users/{username}/*` — read-only user data covered by `search` for fixture purposes
